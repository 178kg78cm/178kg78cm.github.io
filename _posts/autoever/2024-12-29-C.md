교육 과정을 시작하며 C 언어를 임베디드 관점에서 다시 정리했다.

## 공부 방향

- CS 기초 : 운영체제, 어셈블리어 + 컴퓨터구조, C 언어
- 관련 자격증 : 리눅스마스터, 정보처리기능사, 임베디드기사
- 테스팅 자격 : ISTQB 또는 CSTS ([참고](https://blog.naver.com/onycomite/222327398873))

첫 질문은 **"DDRA와 PORTA는 어디에 정의되어 있는가?"** 였다. 아두이노에서 그냥 쓰던 `DDRA`, `PORTA` 같은 이름은 결국 헤더 파일(`<avr/io.h>`)에 **특정 메모리 주소를 가리키는 매크로**로 정의되어 있다. 하드웨어 제어도 C 문법 안에서 이해할 수 있다는 것이 출발점이다.

## 임베디드 섹션

1. **왜 리눅스인가.** 개발 도구(GCC, Make, Git)가 리눅스 기반이고, 임베디드 리눅스 보드도 많다.
2. **C 표준 (ANSI, ISO C)과 GCC**
   그리고 **MISRA C** ★★ (자동차 산업 및 안전 필수 시스템에서 C 코드를 작성할 때 따르는 표준)

### 전처리

C를 컴파일이 아닌 "전처리"만 한 파일은 `.i` 파일로 저장된다. (Visual Studio : 속성 페이지 → 전처리기 → 파일로 전처리 : 예 / GCC : `gcc -E`)

전처리된 파일을 보면 `#define`으로 정의된 부분이 치환된 것을 확인할 수 있다. 이를 통해 매크로 함수가 일반적인 함수의 동작이 아니라 **치환**의 개념이라는 것을 알 수 있다.

- 가벼운 함수 구현은 매크로 함수를 사용해 보자. 함수 호출 오버헤드가 없어 효율이 높아진다.
- 그러나 단순 치환이므로 연산자 우선순위 때문에 계산 오류가 생길 수 있고, 이 오류는 **컴파일 오류로 나타나지 않으므로** 주의해야 한다.
- MAX, MIN, SQUARE, ABS, ARRAY_SIZE, UPPER, LOWER 같은 간단한 매크로에 적합하다.

```c
#define SQUARE(x)  x * x          /* SQUARE(1 + 2) → 1 + 2 * 1 + 2 = 5 */
#define SQUARE2(x) ((x) * (x))    /* 인자와 전체를 괄호로 감싸야 한다 → 9 */
```

### HAL

상위 레이어와 하위 레이어를 나누는 개념이 매우 중요하다.
하위 레이어가 어떤 구조로 되는지 상위 레이어는 관심이 없다. 즉, 어떤 구조인지 몰라도 상위 레이어 개발자는 데이터 값을 얻을 수 있어야 한다. 이것을 **HAL(Hardware Abstraction Layer)** 이라고 한다. 이 개념이 그대로 AUTOSAR의 계층 구조로 이어진다.

### enum

굳이 왜 enum을 사용하는가? **형 안정성과 가독성**이 좋아진다.

- C에서 enum 상수의 타입은 `int`라서 int 대신 써도 문법상 문제는 없다. (enum 변수의 실제 크기는 컴파일러가 정하며, 보통 int 크기다.)
- 하지만 의미 있는 이름으로 허용된 값의 범위를 드러내므로, 정의되지 않은 에러 코드나 상태 값이 들어오는 실수를 줄이고 `switch`에서 빠진 case를 컴파일러 경고로 잡을 수 있다.

### Dangling Pointer

외부 함수에서 지역변수의 주소를 리턴할 경우, 함수가 끝나면 그 지역변수의 스택 공간은 해제된다. 그 주소로 접근하면 어떤 동작이 일어날지 예상할 수 없다.

```c
int *bad(void)
{
    int local = 10;
    return &local;   /* 함수가 끝나면 사라지는 주소 */
}
```

### 구조체

- 구조체를 인자로 넘길 때 포인터로 넘기면 복사 비용 없이 편하게 값을 다룰 수 있다.
- 함수 내부에서 동적할당 후 주소를 리턴하기보다는, main(호출자)의 stack에 선언한 뒤 그 주소를 넘겨주는 방법이 메모리 관리가 수월하다.
- 구조체를 복사할 때, 깊은 복사와 얕은 복사를 유의한다. (포인터 멤버는 주소만 복사된다.)

구조체는 멤버마다 **정렬(Alignment)** 이 맞춰지도록 패딩이 들어가고, 전체 크기는 가장 큰 멤버 크기의 배수가 된다. 즉 4, 4, 1 크기의 멤버가 있다면 가장 큰 4에 맞추어 총 12가 할당된다. [멤버 크기의 합 + 패딩]

```c
struct A { char c; int i; char d; };   /* 1 + (3) + 4 + 1 + (3) = 12 */
struct B { int i; char c; char d; };   /* 4 + 1 + 1 + (2)       = 8  */
```

=> **멤버를 큰 것부터 배치하면 패딩을 줄일 수 있다.** 통신 프레임처럼 바이트 배치가 정확해야 하는 경우에는 패딩을 고려해야 한다.

### 비트 필드

구조체 멤버를 비트 단위로 나눠 쓰는 문법이다. ([정리 노트](https://tulip-taker-d50.notion.site/b2895d56df9b4cf1a66f75ff081a1816#7ce01ac91ada45efaa2ba14b6b5d6158))

```c
typedef struct {
    unsigned int EN   : 1;   /* bit 0 */
    unsigned int MODE : 2;   /* bit 1~2 */
    unsigned int      : 5;   /* 예약 */
    unsigned int DIV  : 8;   /* bit 8~15 */
} CTRL_Bits;
```

- 레지스터의 각 필드를 이름으로 접근할 수 있어 편하다. MCU 벤더 헤더(Infineon의 `Ifx_P_OUT_Bits` 등)도 이 방식을 쓴다.
- 단, 비트 배치 순서와 패딩이 **컴파일러마다 다를 수 있어서** 이식성이 필요한 코드(통신 데이터 등)에서는 비트 연산(마스크와 시프트)을 쓰는 것이 안전하다.

### 공용체

모든 멤버가 같은 메모리 공간을 공유한다. [가장 큰 멤버 크기]

```c
typedef union {
    uint32_t   U;     /* 레지스터 전체를 한 번에 */
    CTRL_Bits  B;     /* 비트 필드로 */
} CTRL;
```

TC275 코드의 `P10_OUT.U`의 `.U`가 바로 이 공용체 패턴이다.

### 연산자로서의 `*`와 `[]`

`*`과 `[]`도 연산자로 해석되기 때문에 `int **arr[2][3]` 같은 선언도 연산자 우선순위 관점에서 이해하면 편하다. `[]`가 `*`보다 우선하므로 arr는 "int** 를 원소로 갖는 2x3 배열"이다.

### volatile과 Memory-mapped I/O

```c
*(volatile unsigned int *)0xABCD = 0x1234;
```

임베디드 시스템에서 하드웨어 레지스터나 특정 메모리 주소에 값을 쓰는 데 사용되는 코드다. (memory mapped IO)

- **volatile** 은 값이 외부 요인에 의해 변경될 가능성이 있을 때 사용한다. 컴파일러가 읽기/쓰기를 최적화로 생략하지 못하게 한다.
- 주로 하드웨어 레지스터, 멀티스레드 공유 변수, 인터럽트 플래그 등의 상황에서 활용된다.
- 하지만 동시성 문제를 해결하려면 volatile만으로는 부족하며, 원자적 연산이나 동기화 기법이 필요하다.

### 주소를 직접 할당하는 방법에 대한 고찰 (ASLR)

```c
int a = 33;
int *pa = NULL;
*(int *)0x0014fcb4 = 99;   /* 디버거로 확인한 a의 주소 */
printf("%d", a);
```

- `pa = (int *)0xABCD;` 이 주소의 실제 위치가 어디가 되는지 모른다.
- PC에서는 ASLR 옵션을 끄고, 확인해 본 a의 주소를 할당하면 정상적으로 a의 값을 바꾸고 출력할 수 있다.
- 그러나 ASLR, 즉 실행할 때마다 주소를 무작위로 배치하는 이유는 **보안** 때문이다. 특정 데이터가 고정된 주소에 있다면 그 주소를 노려 공격할 수 있다.
- 반대로 MCU에서는 레지스터 주소가 **하드웨어로 고정**되어 있어서, 이렇게 주소를 직접 쓰는 것이 정상적인 방법이다.

### 함수 포인터와 콜백

C 언어는 C++과 다르게 "다형성"이 언어 차원에서 정의되지 않는다. 그러나 함수 포인터를 활용하면 다형성과 유사한 기능을 구현할 수 있다.

콜백 함수의 정의 자체는 어렵지 않으나 어디에 쓰는지를 이해하기 쉽지 않다.
호출자가 함수를 바로 호출하는 것이 아니라, 함수를 **등록**해 두고 어떤 조건을 만족하면 등록된 함수가 호출되기 때문에 "콜백"이라고 부른다.

```c
typedef void (*Callback)(int);

static Callback g_onPress = 0;

void Button_Register(Callback cb) { g_onPress = cb; }   /* 등록 */

void Button_ISR(void)                                    /* 이벤트 발생 */
{
    if (g_onPress) g_onPress(1);
}

void Led_On(int id) { /* ... */ }

int main(void)
{
    Button_Register(Led_On);   /* 버튼 모듈은 LED 모듈을 몰라도 된다 */
}
```

- 이벤트 처리, `qsort`의 비교 함수, HAL의 `HAL_xxx_Callback()`이 모두 이 구조다.
- 배열 포인터, 콜백 함수 등을 활용하는 법을 안다면 C++만큼 강력한 활용이 가능하다.

### 헤더 파일과 링크

- 헤더를 여러 번 포함했을 때에는 **헤더 가드**(`#ifndef ... #define ... #endif`)가 동작하여 중복을 막는다.
- 전처리 파일(`.i`)을 통해 헤더 include, define 치환의 흐름을 파악할 수 있다. 이 과정에서 헤더 파일에서 선언과 정의를 동시에 하면 오류가 발생할 수 있음을 이해했다.
  - 헤더에 변수를 **정의**(`int count = 0;`)하면, 그 헤더를 include한 모든 `.c` 파일에 같은 변수가 생겨 **링크 단계에서 중복 정의 오류**가 난다.
  - 그래서 헤더에는 **선언**(`extern int count;`)만 두고, 정의는 하나의 `.c` 파일에서 한다.
- `.h` 파일은 단독으로 컴파일하지 않고(include되어 들어갈 뿐), `.c` 파일이 컴파일 단위다.

| 구분 | Compile error | Linking error |
| --- | --- | --- |
| 시점 | `.c` → `.o` 변환 중 | `.o` 파일들을 하나로 합칠 때 |
| 원인 | 문법 오류, 선언 안 된 이름, 타입 불일치 | 정의를 찾을 수 없음(undefined reference), 중복 정의 |
| 예 | 세미콜론 누락 | 함수 선언만 하고 구현 파일을 빌드에 안 넣음 |

### 전역 변수를 피해야 하는 이유

전역 변수를 쓰지 말아야 하는 가장 큰 이유 중 하나는 접근 범위가 너무 넓어 **모듈 간의 의존성(결합도)을 높이기** 때문이다. 어디서든 값을 바꿀 수 있으니 버그의 원인을 추적하기 어렵다. 꼭 필요하면 `static`으로 파일 안에 숨기고, 접근 함수를 통해서만 바꾸게 한다. ([도요타 급발진 사건](/2025-01-23-도요타SW급발진/)에서도 수많은 전역 변수가 문제로 지적되었다.)
