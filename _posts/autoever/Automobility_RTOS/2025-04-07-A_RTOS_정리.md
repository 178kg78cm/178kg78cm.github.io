## 1. 차량용 실시간 운영체제 표준 OSEK 기본

### 실시간 운영체제 RTOS 개요

- 실시간 시스템은 **결과가 옳은 것뿐 아니라 정해진 시간(Deadline) 안에 나오는 것**까지가 정확성이다.
  - **Hard Real-time** : 데드라인을 한 번이라도 놓치면 시스템 실패 (에어백, 브레이크)
  - **Soft Real-time** : 가끔 놓쳐도 품질 저하에 그침 (멀티미디어)
- 그래서 RTOS는 평균 성능보다 **최악의 경우에도 예측 가능한 동작(Determinism)** 을 중요하게 본다.

### OSEK/VDX 역사

- 1993년 독일 자동차 업계(BMW, Bosch, Daimler, VW 등)가 차량 ECU용 OS 표준을 만들기 위해 **OSEK**을 시작했다.
- 1994년 프랑스의 **VDX**(PSA, Renault)와 합쳐져 OSEK/VDX가 되었고, 이후 **ISO 17356**으로 국제 표준화되었다.
- 목적은 ECU마다 다른 OS를 쓰던 상황을 정리해 **이식성과 재사용성**을 높이고 개발 비용을 줄이는 것이다.

### OSEK/VDX 주요기능

- **정적 구성** : 태스크, 우선순위, 리소스, 알람을 실행 중에 만들지 않고 **OIL 파일로 미리 정의**한다. 동적 메모리 할당이 없어 메모리 사용량과 동작을 예측할 수 있다.
- **Task, Event, Resource, Alarm, Interrupt, Hook, Error 처리**
- **Conformance Class** : 기능 범위에 따라 BCC1, BCC2, ECC1, ECC2로 나눠, 작은 ECU는 필요한 기능만 쓰도록 한다.

| 구분 | Basic Task | Extended Task |
| --- | --- | --- |
| 상태 | Suspended, Ready, Running | + **Waiting** |
| 이벤트 대기 | 불가 | `WaitEvent()` 가능 |
| 스택 | 공유 가능 | 독립 스택 필요 |

### AUTOSAR OS와의 관계

AUTOSAR OS는 **OSEK OS를 기반으로 확장**한 것이다. OSEK API(`ActivateTask`, `GetResource` 등)를 그대로 쓰면서 Schedule Table, Timing/Memory Protection, 멀티코어 지원을 추가했다.

## 2. 태스크 관리 및 스케줄링

### Preemptive / Non-Preemptive 스케줄링

- **Full Preemptive** : 더 높은 우선순위 태스크가 Ready가 되면 즉시 현재 태스크를 선점한다. 응답성이 좋다.
- **Non Preemptive** : 실행 중인 태스크가 끝나거나 `Schedule()`을 호출할 때만 전환된다. 공유 자원 문제가 줄고 컨텍스트 스위칭 비용이 적다.
- OSEK은 태스크마다 둘 중 하나를 고를 수 있다(Mixed). 실습에서 OIL의 `SCHEDULE = FULL` 설정이 이것이다.

### 우선순위 기반 스케줄링

- OSEK은 **고정 우선순위** 방식이고, 같은 우선순위끼리는 활성화된 순서(FIFO)로 실행한다.
- Starvation을 신경 쓰지 않고 항상 우선순위에 따른다. 그래서 우선순위 설계 자체가 시스템 설계다.
- 우선순위에 따라 실행 흐름이 어떻게 달라지는지는 [RTOS 1 실습](/2025-01-24-RTOS1/)에서 확인했다.

### Rate Monotonic Scheduling (RMS)

- 주기 태스크에서 **주기가 짧을수록 높은 우선순위**를 주는 방식이다.
- 고정 우선순위 방식 중 최적이라는 것이 증명되어 있다. (RMS로 스케줄 불가능하면 다른 고정 우선순위로도 불가능)

### Schedulability Analysis

태스크 집합이 모든 데드라인을 지킬 수 있는지 미리 분석한다.

- **CPU 이용률 검사 (Liu & Layland)** : 태스크 n개의 이용률 합이 다음 이하이면 RMS로 스케줄 가능하다.

```text
U = Σ (Ci / Ti) ≤ n(2^(1/n) - 1)
n = 1 → 1.0,  n = 2 → 0.828,  n = 3 → 0.780,  n → ∞ → 약 0.693
```

- 이 조건은 **충분조건**이라, 넘는다고 무조건 불가능한 것은 아니다. 정확히 보려면 **응답 시간 분석(Response Time Analysis)** 을 한다.

```text
Ri = Ci + Σ(j ∈ 더 높은 우선순위) ⌈Ri / Tj⌉ × Cj      (Ri ≤ Di 이면 OK)
```

- 여기서 Ci는 **최악 실행 시간(WCET)** 이다. 평균 실행 시간으로 분석하면 의미가 없다.

### 인터럽트 분류 및 중첩 인터럽트

| 구분 | Category 1 ISR | Category 2 ISR |
| --- | --- | --- |
| OS 관여 | 없음 | OS가 관리 |
| OS API 호출 | 불가 | 일부 가능 (`ActivateTask`, `SetEvent` 등) |
| 오버헤드 | 가장 작음 | 상대적으로 큼 |
| 용도 | 매우 빠른 처리 | 처리 후 태스크를 깨워야 할 때 |

- 인터럽트도 우선순위가 있어서, 높은 우선순위 인터럽트가 낮은 ISR을 선점할 수 있다(중첩 인터럽트).
- 모든 ISR은 모든 태스크보다 우선한다. 그래서 **ISR은 짧게, 무거운 처리는 태스크로** 넘기는 것이 원칙이다.

## 3. 리소스 보호 기법

### Race Condition과 Locking

- 여러 태스크/ISR이 같은 데이터를 동시에 읽고 쓰면, 실행 순서에 따라 결과가 달라지는 **경쟁 상태**가 생긴다.
- `x++`도 Load → Add → Store 세 단계라서 중간에 선점되면 값이 사라질 수 있다.
- 보호 방법 : 인터럽트 비활성화(`SuspendAllInterrupts`), 리소스(`GetResource/ReleaseResource`), 멀티코어에서는 Spinlock

### Priority Inversion Problem

공유 자원 때문에 높은 우선순위 태스크가 낮은 태스크를 기다리고, 그 사이에 중간 우선순위 태스크가 끼어들어 대기 시간이 무한정 길어지는 문제다. 자세한 시나리오는 [우선순위 역전 현상](/2025-03-20-우선순위역전현상/)에 정리했다.

### Priority Inheritance Protocol (PIP)

자원을 기다리는 높은 우선순위를 자원 보유 태스크가 **물려받는다**. 런타임에 처리하지만 데드락은 막지 못한다.

### Priority Ceiling Protocol (PCP)

자원마다 사용하는 태스크 중 최고 우선순위(Ceiling)를 정해 두고, 자원을 잡는 **즉시 Ceiling으로 올린다**. 블로킹은 최대 한 번이고 데드락도 막는다. **OSEK OS가 채택한 방식**이다.

## 4. AUTOSAR OS 심화

### Scalability Class

| Class | 기능 |
| --- | --- |
| SC1 | OSEK OS + Schedule Table |
| SC2 | SC1 + **Timing Protection** |
| SC3 | SC1 + **Memory Protection** (OS-Application) |
| SC4 | SC2 + SC3 (모두) |

### Schedule Table

- 하나의 카운터를 기준으로 **정해진 시점(Expiry Point)마다 태스크 활성화/이벤트 설정**을 하는 정적 테이블이다.
- 알람 여러 개로 만들던 주기 동작을 한 테이블로 묶어, 태스크 간 **상대적인 실행 시점(오프셋)** 을 보장한다.
- 외부 시간(예: FlexRay 글로벌 시간)에 동기화할 수도 있다.

### Timing/Memory Protection

- **Timing Protection** : 한 태스크가 예상보다 오래 실행되면 다른 태스크의 데드라인이 깨진다. 이를 감시한다.
  - Execution Budget : 1회 실행 시간 상한
  - Time Frame : 최소 활성화 간격 (너무 자주 실행되는 것 방지)
  - Lock Budget : 리소스/인터럽트 잠금 시간 상한
- **Memory Protection** : MPU로 OS-Application별 메모리 접근 권한을 나눠, 한 SWC의 버그가 다른 SWC의 데이터를 망가뜨리지 못하게 한다. 서로 다른 ASIL의 소프트웨어가 한 ECU에 같이 있을 때(Freedom from Interference) 필수다.
- 위반이 감지되면 **ProtectionHook**이 호출되고, 태스크 종료/OS-Application 재시작/시스템 종료 중 대응을 선택한다.

### End-to-End Delay 분석

센서 입력이 여러 태스크(입력 처리 → 제어 연산 → 출력)를 거쳐 액추에이터 출력까지 가는 경로를 **원인-결과 체인(Cause-Effect Chain)** 이라 한다. 태스크마다 주기가 다르면(멀티레이트) 데이터가 다음 태스크에서 바로 쓰이지 않고 기다리는 시간이 생긴다.

### Reaction Time, Data Age 이해

- **Reaction Time** : 입력이 바뀐 순간부터, 그 변화가 **처음으로** 출력에 반영되기까지의 시간 (얼마나 빨리 반응하는가)
- **Data Age** : 출력이 나가는 순간, 그 출력이 근거로 한 입력 데이터가 **얼마나 오래된 것인가** (얼마나 최신 데이터로 제어하는가)

예를 들어 10ms 태스크가 만든 값을 50ms 태스크가 읽으면, 최악의 경우 거의 한 주기(50ms)만큼 반응이 늦어질 수 있다. 그래서 체인을 이루는 태스크들의 **주기와 오프셋(Schedule Table)** 을 함께 설계해야 한다.
