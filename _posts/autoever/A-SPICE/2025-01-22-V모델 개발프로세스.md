## V-Model
개발 생명주기를 V자 모양으로 표현한 모델이다. 왼쪽으로 내려가며 **분해(설계)** 하고, 오른쪽으로 올라가며 **통합(검증)** 한다. 같은 높이의 단계끼리 짝을 이룬다.

```text
고객 요구사항 ───────────────────────────────────────── 인수 테스트
  시스템 요구사항 분석 ─────────────────────── 시스템 검증 (Qualification Test)
    시스템 아키텍처 설계 ─────────────── 시스템 통합 테스트
      SW 요구사항 분석 ─────────── SW 검증 (Qualification Test)
        SW 아키텍처 설계 ─────── SW 통합 테스트
          SW 상세 설계 ──── SW 유닛 검증
                  \  구현  /
```

- 왼쪽의 각 단계가 끝날 때 **오른쪽에서 사용할 테스트 기준(검증 기준)을 미리 만든다.**
- 문제가 생기면 같은 높이의 왼쪽 단계로 돌아가 원인을 찾을 수 있다. (예: 통합 테스트 실패 → 아키텍처 설계 확인)
- 이 모든 출발점이 **요구사항**이다. 그래서 V 모델의 맨 위 왼쪽, 요구사항부터 정리한다.

## 요구사항이란?
### 정의
현실 세계의 문제를 해결하기 위해 **고객에 의해 요구**되거나 **표준** 등을 만족시키기위해 **제품이 가져야하는 서비스 또는 제약사항**
### 분류
- 고객 요구사항 : 고객이 바라는 **Needs**
- 제품 요구사항 : 고객 요구사항을 만족하기 위해 **제품이 수행해야하는 개발관점의 요구사항**
- 기능적 요구사항 : 목표 달성을 위해 제공해야하는 **행위적(기능적) 속성**
- 비기능적 요구사항 : **품질기준**(성능, 안전성, 사용성 등)을 만족시키기위해 가져야 하는 속성

## 소프트웨어 요구 공학
소프트웨어 개발을 위한 요구사항을 추출, 분석, 명세, 검증하며 개발된 요구사항의 변경 및 추적을 관리하는 공학적 접근

- 요구사항 도출 &rarr; 요구사항 분석 &rarr; 요구사항 명세 &rarr; 요구사항 검증

분석하면 risk가 나오는데 이게 다시 플랜에 포함이 되어야 함..

명세화의 프로세스를 갖추어 모든 결과물의 품질이 일정하게 나오도록 하는 것이 중요하다.
명세 방법을 선정해야한다.

- 객체지향 분석

#### EARS 방식으로 요구사항 작성하기
EARS(Easy Approach to Requirements Syntax)는 자연어 요구사항의 모호함을 줄이기 위해 **정해진 문장 틀**을 쓰는 방법이다.

| 유형 | 틀 | 예시 |
| --- | --- | --- |
| Ubiquitous (항상) | The `<시스템>` shall `<응답>` | 시스템은 시동 중 ECU 동작 LED를 켜야 한다. |
| Event-driven | **When** `<트리거>`, the `<시스템>` shall `<응답>` | 열선 스위치가 눌리면, 시스템은 열선을 켜야 한다. |
| State-driven | **While** `<상태>`, ... | 열선이 동작하는 동안, 시스템은 상태 LED를 켜야 한다. |
| Unwanted behavior | **If** `<조건>`, **then** ... | 다이얼 입력이 범위를 벗어나면, 시스템은 열선을 끄고 오류를 기록해야 한다. |
| Optional | **Where** `<기능 포함 시>`, ... | 통풍 기능이 있는 경우, 시스템은 ... |

한 문장에 하나의 요구사항, 측정 가능한 표현을 쓰면 검증 기준(BP5)을 만들기도 쉬워진다.

### sw안전 요구사항 개발방법
- 위험원 분석 기법
    - **HAZOP** : "없음, 많음, 적음, 반대, 늦음" 같은 가이드워드를 기능에 대입해 의도에서 벗어나는 경우를 찾는다.

- 안전 분석
    FMEA(Failure Mode and Effects Analysis)/FTA 등의 안전 분석을 수행하고 대책을 찾으면 이를 SW 안전 요구 사항으로 도출한다.

  -   Failure Mode and Effects Analysis => Bottom up으로 분석하는 방법
  -   Fault Tree Analysis => Tree 형태로 top down 분석 방법
  -   FMEA는 "이 부품이 고장 나면 어떤 일이 생기나"(원인 → 결과), FTA는 "이 사고가 나려면 무엇이 고장 나야 하나"(결과 → 원인)를 본다. 둘을 함께 쓰면 빠진 고장을 줄일 수 있다.


### 요구사항 검증
이해당사자 기대사항이 의도한대로 요구사항이 추출 및 분석되어 소프트웨어 요구사항 명세서가 작성되었는지를 검토/확인하는 활동

1. **완전성** : 필요한 요구사항이 빠짐없이 있는가
2. **명확성** : 한 가지로만 해석되는가
3. **실현가능성** : 주어진 기술, 일정, 비용으로 구현 가능한가
4. **추적가능성** : 상위 요구사항, 설계, 테스트와 연결되어 있는가

검증 방법으로는 리뷰(Walkthrough, Inspection), 체크리스트, 프로토타이핑, 모델 기반 시뮬레이션이 쓰인다.
