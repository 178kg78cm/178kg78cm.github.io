## 품질
품질이란 명시적, 묵시적 요구를 만족시키는 제품 또는 서비스 능력에 관한 특성이다. 우리는 품질의 정의를 잊지 않아야한다.

## 소프트웨어 품질
ISO/IEC 25010은 소프트웨어 제품 품질을 8가지 특성으로 정의한다.

| 특성 | 의미 |
| --- | --- |
| 기능 적합성 | 요구된 기능을 정확하고 완전하게 제공하는가 |
| 성능 효율성 | 시간(응답, 처리량), 자원 사용이 적절한가 |
| 호환성 | 다른 시스템과 공존하고 정보를 교환할 수 있는가 |
| 사용성 | 배우고 사용하기 쉬운가 |
| 신뢰성 | 정해진 조건에서 고장 없이 동작하고, 고장 시 복구되는가 |
| 보안성 | 허가된 사용자만 접근하고 데이터를 보호하는가 |
| 유지보수성 | 수정, 분석, 테스트가 쉬운가 |
| 이식성 | 다른 환경으로 옮기기 쉬운가 |

테스팅은 이 특성들을 **확인 가능한 형태로 검증**하는 활동이다.

## 소프트웨어 테스팅
정상 조건 및 비정상 조건(결함, 버그) 사이의 차이점을 발견하기 위하여 소프트웨어 항목을 분석하고, 분석된 항목의 특성을 평가하는 프로세스. 즉, 결함을 발견하려는 의도를 가지고 프로그램을 실행하는 프로세스이다.

테스팅은 결함을 발견하는 과정으로 버그를 바로잡는 디버깅과는 구분해야 한다.

### A-SPICE의 Software Unit Verification (SWE.4)
- 상세 설계와 코드가 맞는지 **유닛 단위**로 검증한다.
- 정적 검증(코딩 규칙 검사, 정적 분석, 코드 리뷰)과 동적 검증(유닛 테스트, 커버리지 측정)을 함께 쓴다.
- 검증 기준(Verification criteria)은 상세 설계에서 나온다.

### A-SPICE의 Software Integration and Integration Test (SWE.5)
- 유닛을 아키텍처 설계에 따라 통합하면서, **컴포넌트 간 인터페이스와 동적 동작**(호출 순서, 타이밍, 자원 사용)을 검증한다.
- 테스트 케이스는 SW 아키텍처 설계에서 나온다.

### A-SPICE의 Software Qualification Test (SWE.6)
- 통합이 끝난 소프트웨어 전체가 **SW 요구사항을 만족하는지** 검증한다.
- 테스트 케이스는 SW 요구사항에서 나오며, 요구사항 ↔ 테스트 케이스 ↔ 결과 사이에 양방향 추적성이 있어야 한다.

=> 세 프로세스 모두 **회귀 테스트(Regression) 전략**을 요구한다. 수정이 생겼을 때 어떤 테스트를 다시 돌릴지 미리 정해 두어야, 변경이 다른 기능을 망가뜨리지 않았음을 보장할 수 있다.


강의 중 요구사항 단계에서 강조된 용어가 **"엘리시테이션(Elicitation)"** 이다.

### Elicitation이란?
Elicitation은 요구사항 분석 단계에서 **이해관계자(Stakeholders)**로부터 **요구사항(Requirements)**을 수집하고 도출하는 과정을 뜻한다.

시스템 개발, 프로젝트 관리, 또는 SPICE(Software Process Improvement and Capability dEtermination) 같은 프로세스 개선 활동에서 중요한 단계이다.
일반적으로 이해관계자와 소통하여 프로젝트의 목표와 필요를 명확히 정의하기 위한 다양한 기술과 도구를 사용한다.

- 주요 Elicitation 기법
  -   인터뷰(Interviews) : 이해관계자와 직접 대화하며 요구사항을 파악.
  -   워크숍(Workshops) : 그룹 단위로 논의하며 요구사항을 수집.
  -   설문조사(Surveys/Questionnaires) : 대규모 이해관계자로부터 데이터 수집.
  - 관찰(Observation) : 현재 프로세스나 사용 환경을 관찰하며 요구사항 도출.
  - 프로토타이핑(Prototyping) : 샘플 모델을 만들어 피드백을 받아 요구사항 확정


> V 모델의 기반에서 추적성과 일관성을 적용해보면 좋을거같다.

### 소프트웨어 개발 단계별 테스팅 활동
| 구분 | 대상 | 담당자 | 환경 | 방법 |
| --- | --- | ---- | --- | --- |
| 단위 테스팅 | 단위모듈 | 개발자 | 개발환경 | 화이트 박스 |
| 통합 테스팅 | 통합 모듈 | 개발자 | 개발환경 | 그레이 박스 |
| 시스템 테스팅 | 전체 시스템 | 테스터(제3자) | 실제 유사 환경 | 블랙 박스 |
| 인수 테스팅 | 최종 소프트웨어 | 사용자, 고객 | 실제 환경 | 블랙 박스 | 

### 블랙박스 테스팅과 화이트박스 테스팅
- 블랙박스 테스팅
  - 명세 기반 테스팅이라고도 불림.
  - 코드를 제외하고 출력값의 결함을 찾는 방식
- 화이트박스 테스팅
  - 구조기반 테스팅이라고도 불림.
  - 코드 내의 모든 독립적인 경로를 수행해보면서 결함을 찾아내는 방식
  - 프로그램 코드로부터 테스트 케이스 추출

#### 블랙박스 테스팅 종류
- **동등분할** : 입력을 같은 결과를 내는 그룹으로 나누고 그룹마다 대표값 하나만 테스트 (예: 나이 0~17 / 18~64 / 65~)
- **경계값분석** : 결함이 몰리는 그룹의 경계에서 테스트 (예: 17, 18, 64, 65)
- **의사결정테이블** : 조건의 조합과 그에 따른 동작을 표로 만들어 빠짐없이 테스트

#### 화이트박스 테스팅 종류
- **함수 커버리지** : 모든 함수가 한 번 이상 호출되었는가
- **문장 커버리지 (Statement)** : 모든 문장이 한 번 이상 실행되었는가
- **결정 커버리지 (Decision/Branch)** : 모든 분기(if의 참/거짓)가 한 번 이상 실행되었는가
- **조건 커버리지 (Condition)** : 결정 안의 개별 조건(`A && B`의 A, B 각각)이 참/거짓을 모두 가졌는가
- **MC/DC** : 각 조건이 **독립적으로 결과에 영향을 주는 것**을 보이는 커버리지. ISO 26262 ASIL D에서 강하게 권장된다.
- **경로 커버리지** : 가능한 모든 실행 경로를 테스트. 얘가 좀 신기했는데, 루프가 있으면 경로 수가 폭발해서 현실적으로는 순환 복잡도만큼의 **기본 경로(Basis Path)** 만 테스트한다.

> 화이트박스 블랙박스 테스트 케이스를 만들어보는 실습을 해보았는데 의견차이가 심했다.
> 처음에 요구사항을 확실히 정하고 이해하는 과정이 중요하다.

A SPICE는 how 보다는 what에 대해서 정의를 많이 한 표준
그러나 ISO 26262는 How에 대해서 많이 서술되어 있다.

A SPICE는 "무엇을 해야 하는가(산출물, 목적)"를 정하고 방법은 조직에 맡긴다. ISO 26262는 ASIL별로 "어떤 기법을 써야 하는가"까지 표로 정해 둔다. 그래서 둘을 함께 적용하면 프로세스의 뼈대는 A-SPICE로, 안전을 위한 구체적인 방법은 26262로 채우게 된다.


## 소프트웨어 형상 관리
프로세스를 거치는 동안 나온 모든 작업 산출물이 형상이다.
즉, 요구사항 명세서, 설계서, 테스트 결과 등이 모두 형상이다.

형상관리란 이런 모든 것들의 consistency를 확보해서 **무결성(integrity)**을 얻는 과정을 지속적으로 추적(Traceablity)하는 과정이다.

### A-SPICE의 Configuration Management (SUP.8)

형상 관리 전략 수립 → 형상 항목 식별 → 브랜치/병합 관리 → 변경 통제 → **Baseline 관리** → 형상 상태 보고 → 형상 검증 순으로 BP가 구성된다. 그중 핵심은 BP 6. **Baseline 관리**다.

- Baseline : 공식적으로 검토되고 합의된 산출물의 묶음. 이후 변경은 정해진 변경 통제 절차로만 가능하다.
- 예 : 릴리스 시점의 요구사항 명세서 v1.2 + 설계서 v1.1 + 소스 코드 태그 + 컴파일러 버전 + 테스트 결과를 하나의 베이스라인으로 묶는다.


### 형상 식별
형상 관리할 대상 항목을 식별하고 베이스라인 기준을 정하는 과정
- 형상 항목 설정
- 형상 식별자 정의
- Baseline 기준 설정

### 형상 통제
형상 관리 하기 위한 대상 산출물 목록 및 개발 도구 등을 선정
- 요구사항 명세서
- 설계서
- 소스코드
- 컴파일러


### 형상 식별자 정의
- 형상 항목에 유일한 이름과 버전 등의 식별 체계를 정의하는 것으로 산출물의 파일 이름으로 활용됨.

### 형상 감사
형상 관리 계획에 따라 관리 활동의 진행 여부를 확인하는 과정
- 형상 관리 계획 준수 여부
- 베이스라인 설정 적절성
- 형상 통제의 적절성


## 소프트웨어 추적 관리

추적성(Traceability)은 산출물 사이의 연결을 관리하는 것이다.

```text
고객 요구사항 ↔ 시스템 요구사항 ↔ SW 요구사항 ↔ SW 아키텍처 ↔ 상세 설계 ↔ 코드
                                     ↕                ↕            ↕
                               Qualification Test  Integration Test  Unit Test
```

- **순방향** : 요구사항이 설계, 코드, 테스트로 모두 구현/검증되었는가 (빠진 요구사항 확인)
- **역방향** : 이 코드/테스트는 어떤 요구사항 때문에 존재하는가 (불필요한 기능, 근거 없는 코드 확인)
- **변경 영향 분석** : 요구사항 하나가 바뀌면 어떤 설계, 코드, 테스트를 다시 봐야 하는지 바로 알 수 있다.
- 추적성이 있어야 **일관성**(연결된 산출물끼리 내용이 맞는지)도 확인할 수 있다. 그래서 A-SPICE의 핵심 컨셉이 "추적성과 일관성"이다.

### ALM (Application Lifecycle Management)

엑셀로 추적표를 관리하면 규모가 커질수록 유지가 불가능하다. 그래서 요구사항, 설계, 테스트, 변경 요청을 한 도구 안에서 링크로 관리하는 ALM 도구를 쓴다.

- 강의에서 언급된 도구 : codeBeamer, PTC **Integrity**(예전에 많이 쓰임), Siemens **Polarion**(최근 많이 쓰임)
- 강의 메모에는 이 도구들을 현대오토에버와 함께 적어 두었다. 실제 현업에서 어떤 도구를 쓰는지는 회사와 프로젝트마다 다르다.
