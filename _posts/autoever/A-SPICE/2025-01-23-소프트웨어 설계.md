## 소프트웨어 아키텍쳐 설계
상위 수준에서 **소프트웨어 구성 요소들 간의 관계**로 구성된 전체적인 구조를 설계하는 활동

### 원칙
1. **높은 응집도** : 하나의 모듈은 하나의 책임에 관련된 기능만 갖는다.
2. **낮은 결합도** : 모듈 간 의존을 최소화하고, 정해진 인터페이스로만 통신한다. (전역 변수 공유는 결합도를 크게 높인다.)

### 역할
- 여러 이해관계자의 의사소통 수단
- 시스템 품질 속성 사용 또는 억제 기준
- 변경에 대한 원인 파악 및 유연한 대처 가능
- 재사용가능한 소프트웨어 구성 요소 확보 수단
  
### 품질 속성
ISO/IEC 9126의 품질 특성 (현재는 ISO/IEC 25010으로 대체)

- 기능성
- 신뢰성
- 사용성
- 효율성
- 유지보수성
- 이식성

## 소프트웨어 구현 및 통합
### 소프트웨어 구현
개별 소프트웨어 단위를 실행가능한 형태로 구현하고 이를 문서화하는 활동으로 프로그래밍이라고 함.

#### C언어
- MISRA-C ★★★★★
- CERT C CODING STANDARD (SEI)
- HIS Source Code Metrics


#### MISRA C : 2012
C 언어 기반 프로그램의 신뢰성, 안전성, 호환성을 확보하기 위해 MISRA에서 개발한 156개의 Rule set


#### 순환 복잡도 (Cyclomatic Complexity)

MS 순환복잡도는 Microsoft의 개발 안내 지침에 따라 소프트웨어의 관리 코드 복잡성과 유지 관리 용이성을 측정하는 지표입니다. 
순환복잡도(Cyclomatic Complexity)는 조건부 분기의 수와 복잡성에 따라 결정되며, 프로그램의 이해 난이도를 나타냅니다. 
순환복잡도를 측정하는 방법은 다음과 같습니다. 

1. 프로그램을 제어 흐름 그래프로 변환합니다.
2. `V(G) = E - N + 2` (E : 간선 수, N : 노드 수) 또는 간단히 **조건 분기(if, while, for, case, &&, ||) 수 + 1**로 계산합니다.

Microsoft의 개발 안내 지침에서는 순환복잡도를 25 이하로 유지할 것을 권고하고 있습니다. 자동차 업계에서 널리 쓰는 **HIS Metrics**는 함수당 10 이하를 권장합니다. 복잡도가 높을수록 테스트해야 할 경로가 늘어나고 결함 가능성이 커집니다.

#### 코드 리펙토링
The process of restructuring existing computer code without changing its external behavior

- 코드 가독성/이해도 향상
- 결함을 발견하기 쉬움
- 프로그램 속도 향상
- 소프트웨어 설계 개선

### 소프트웨어 통합
개발된 단위 모듈 소프트웨어들을 통합 계획에 따라 통합하여 완전한 소프트웨어 구조를 개발하는 활동

#### A-SPICE의 Software Integration and Integration Test
BP1. 소프트웨어 통합 계획을 수립하라.
BP2. 회귀 테스트 전략을 포함한 소프트웨어 통합 테스트 전략을 수립하라
BP1, BP2는 4.0에 들어가서는 사라졌다. why? Plan보다 Do에 집중하기 때문에, 혼동을 막기 위해서 사라졌다. (계획 수립은 프로젝트 관리 프로세스의 몫으로 정리)
이후 BP는 통합 수행, 테스트 명세 개발, 테스트 수행, 양방향 추적성, 일관성, 결과 의사소통으로 이어진다.

> A SPICE의 각 과정에서 BP를 이해할 때, 그 사이의 두 단계를 연관지어서 해석해야 올바른 해석이 된다.

#### 빅뱅 통합
모든 모듈을 한꺼번에 합친 뒤 테스트한다.
- 준비가 간단하지만, 오류가 나면 **어느 모듈 사이의 문제인지 찾기 어렵다.**
- 작은 시스템에서만 적합하다.

#### 하향식 통합
상위 모듈부터 시작해 아래로 내려가며 통합한다.
- 아직 없는 하위 모듈은 **스텁(Stub)** 으로 대신한다.
- 주요 제어 흐름과 구조를 일찍 검증할 수 있다.
- 하위의 하드웨어 의존 기능은 늦게 검증된다.

#### 상향식 통합
하위 모듈부터 시작해 위로 올라가며 통합한다.
- 아직 없는 상위 모듈은 **드라이버(Driver, 테스트 하네스)** 로 대신한다.
- 하드웨어와 가까운 기능(드라이버, BSW)을 먼저 확실히 검증할 수 있어 임베디드에 자주 쓰인다.
- 전체 동작은 마지막에야 확인된다.

실제로는 상향식과 하향식을 섞은 **샌드위치(혼합) 통합**을 많이 쓴다.

#### 지속적 통합(Continuous Integration)
SW **통합 오류**를 **개발 초기**부터 **예방**하는 것
- 개발자가 작은 단위로 자주 저장소에 병합하고, 병합할 때마다 **자동 빌드 + 자동 테스트 + 정적 분석**을 실행한다.
- 통합을 마지막에 몰아서 하는 빅뱅의 문제를 매일 조금씩 나눠서 해결하는 방식이다.
- 도구 : Jenkins, GitLab CI, GitHub Actions 등


### 소프트웨어 결함
용어를 구분해서 쓴다. (IEEE / ISTQB 기준)

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| **Error (실수)** | 사람이 저지른 실수 | 요구사항을 잘못 이해함 |
| **Fault / Defect / Bug (결함)** | 실수로 인해 산출물(코드, 문서)에 남은 잘못 | 조건문의 `<`를 `<=`로 잘못 씀 |
| **Failure (고장)** | 결함이 실행되어 시스템이 기대와 다르게 동작 | 경계값에서 잘못된 결과 출력 |

- 결함은 **발견이 늦을수록 수정 비용이 커진다.** 요구사항 단계의 결함을 출시 후 고치면 비용이 수십~수백 배가 된다는 것이 V 모델 왼쪽 품질을 강조하는 이유다.


### Verification & Validation
일반적으로 V model 에서 각 단계의 산출물이 명세를 만족하는지 보는 것이 Verification, 최종 제품이 고객의 의도를 만족하는지 보는 것이 Validation이다.

- 검증
  - 제품이 올바르게 만들어지고 있는가?
    - 소프트웨어가 요구사항에 부합하여 구현되었음을 보장.
    - 요구사항 명세서 등 Spec에 맞게 올바른 방법으로 제품을 만들고 있음을 보장.

- 확인
  - 올바른 제품을 만들고 있는가?
    - 소프트웨어가 사용자가 의도한 요구사항에 따라 구현되었음을 보장.
    - 사용자가 의도한 환경이나 목적에 맞게 올바른 제품을 만들고 있음을 보장.


> V 모델의 모든 프로세스를 따르는 것은 못하더라도 최소한 Check list, Review 등을 이용해서 프로세스의 일정부분을 따라하려 했고 품질을 갖출 수 있었다.

#### 검증 및 확인 기법 분류
-  Static (실행하지 않고 검사)
   -  Review(Check list), **Inspection**
   -  **Static Analysis base on tool** 
-  Dynamic (실행하면서 검사)
   -  White Box & Black Box Testing
   -  Unit, Integration, system, Acceptance Testing
