일주일 동안 배운 자동차 소프트웨어 개발 프로세스 과정을 마무리하며 정리한다.

차량 관련 모든 표준(안전, 보안)은 A-SPICE 기반으로 추가적으로 정의되고 있다.

## 과정 목표

- 자동차 소프트웨어 개발 프로세스의 필요성 인식
- 두 가지 표준 **A-SPICE**와 **ISO 26262**의 상관관계 이해
- 프로세스의 중요성과 각 단계별 산출물이 어떤 특징을 가지고 있는가

## 배운 순서

1. **전장 시스템에서 왜 소프트웨어가 중요한가? (feat. 보안)**
   - 소프트웨어 정의, 소프트웨어 공학의 필요성
   - 프로세스의 개념 이해
   - 최상위 수준의 프로세스, 생명주기(Life Cycle)에 대한 이해
   - → [자동차 소프트웨어 개발 프로세스](/2025-01-22-자동차-소프트웨어-공학/)
2. **A-SPICE는 왜 만들어졌는가**
   - 개념 : Full name 기반으로 보면 결국 **프로세스**를 개선하고 능력을 평가하는 모델
   - PRM / PAM : 프로세스 ID, 이름, 목적, 성과, 수행 지표(BP, WP)
   - 능력 수준은 **CL2**가 중요하다. (계획하고 관리되는 수준이 OEM 요구의 기준선)
   - 핵심 컨셉 중 가장 중요한 것은 **추적성과 일관성**
   - → [A-SPICE](/2025-01-22-A-SPICE/)
3. **안전이 무엇인가 → 기능안전 → 소프트웨어 안전**으로 나아가며 이해
   - ISO 26262 Hazard Analysis(HARA)
   - → [SW 안전과 ISO 26262](/2025-01-22-ISO-26262/)
4. **실습을 쭉 따라가며 정리**
   - 요구사항 → 설계 → 구현/통합 → 테스트
   - → [V-Model 개발 프로세스](/2025-01-22-V모델-개발프로세스/), [소프트웨어 설계](/2025-01-23-소프트웨어-설계/), [소프트웨어 테스팅](/2025-01-24-소프트웨어-테스팅/)
5. **형상관리 / 추적관리**
   - 모든 산출물을 식별하고 베이스라인으로 관리, 요구사항부터 테스트까지 양방향 추적

## 안전과 보안의 연결

- A-SPICE를 따라 보안 규약이 새로 정립되고 있다. 전장 소프트웨어가 표준적·정책적으로 발전하는 근간에는 A-SPICE가 기반이 된다.
  - 기능안전 : ISO 26262 (프로세스는 A-SPICE와 맞물림)
  - 사이버보안 : ISO/SAE 21434, **A-SPICE for Cybersecurity**
- 분석 기법도 같은 구조를 가진다.

| 구분 | 안전 (Safety) | 보안 (Security) |
| --- | --- | --- |
| 다루는 것 | 고장(Malfunction)으로 인한 위험 | 의도적 공격으로 인한 위험 |
| 분석 | **HARA** (Hazard Analysis and Risk Assessment) | **TARA** (Threat Analysis and Risk Assessment) |
| 등급 | ASIL (A~D) | CAL (Cybersecurity Assurance Level) |
| 위험원 식별 기법 | **HAZOP** (가이드워드로 기능 이탈 분석), FMEA, FTA | STRIDE, 공격 트리 |

- HAZOP : "없음(No)", "더 많이(More)", "더 적게(Less)", "반대로(Reverse)", "늦게(Late)" 같은 가이드워드를 기능에 대입해서, 기능이 의도와 다르게 동작하는 경우를 체계적으로 찾는 기법
