## 자동차 소프트웨어 개발의 필요성 인식

차량 기능의 대부분이 소프트웨어로 구현되면서, OEM은 여러 협력사가 만든 소프트웨어의 품질을 **결과물만 보고는 판단하기 어려워졌다.** 그래서 "이 회사는 소프트웨어를 믿을 만한 방식으로 만드는가"를 평가하는 기준이 필요해졌고, 그것이 A-SPICE다.

## A-SPICE (Automotive SPICE)

### A-SPICE란? - De facto STD

**A-SPICE (Automotive Software Process Improvement and Capability dEtermination)** 는 자동차 소프트웨어 개발의 품질과 효율성을 높이기 위해 사용되는 프로세스 평가 모델이다. ISO/IEC 15504(현재 ISO/IEC 330xx)를 기반으로 독일 자동차 업계(VDA)가 자동차 산업에 맞게 만들었고, 공식 국제 표준은 아니지만 사실상의 업계 표준(De facto standard)이다.

` 자동차 부품 업체들의 소프트웨어 프로세스를 개선하고 능력을 평가하기 위한 기준을 제시한 프로세스 모델 `

---

### A-SPICE의 목적

1. **프로세스 품질 보증** : 소프트웨어 개발의 체계적이고 반복 가능한 품질 관리를 보장
2. **효율적인 개발** : 표준화된 개발 방법론을 통해 프로젝트 시간과 비용 절감
3. **리스크 관리** : 프로젝트 진행 중 발생할 수 있는 리스크 최소화
4. **고객 및 규제 요구사항 준수** : 자동차 제조업체와 공급업체 간 협력에서 요구되는 품질 기준 충족

---

### A-SPICE의 핵심 요소

#### 1. 프로세스 그룹

A-SPICE는 프로세스를 다음 3가지 카테고리로 나눈다.

- **Primary Life Cycle Processes (주요 생명주기 프로세스)**
  - 시스템 및 소프트웨어 개발의 핵심 활동
  - 예 : 획득(ACQ), 공급(SPL), 시스템 엔지니어링(SYS.1~5), 소프트웨어 엔지니어링(SWE.1~6)
- **Supporting Life Cycle Processes (지원 생명주기 프로세스)**
  - 주요 프로세스를 지원하는 활동
  - 예 : 품질 보증(SUP.1), 형상 관리(SUP.8), 문제 해결 관리(SUP.9), 변경 요청 관리(SUP.10)
- **Organizational Life Cycle Processes (조직 생명주기 프로세스)**
  - 조직 차원의 관리와 개선
  - 예 : 프로젝트 관리(MAN.3), 리스크 관리(MAN.5), 프로세스 개선(PIM.3), 재사용 관리(REU.2)

---

#### 2. 프로세스 능력 수준 (Capability Levels)

A-SPICE는 프로세스의 성숙도를 0~5까지의 수준으로 평가한다.

| Level | 이름 | 의미 | 프로세스 속성(PA) |
| --- | --- | --- | --- |
| 0 | Incomplete | 프로세스가 수행되지 않거나 목적을 달성하지 못함 | |
| 1 | Performed | 프로세스가 수행되고 결과물이 생성됨 (체계적이지 않음) | PA 1.1 프로세스 수행 |
| 2 | **Managed** | **계획되고 모니터링되며, 산출물이 관리됨** | PA 2.1 수행 관리, PA 2.2 산출물 관리 |
| 3 | Established | 조직의 표준 프로세스가 정립되어 여러 프로젝트가 일관된 프로세스를 따름 | PA 3.1 프로세스 정의, PA 3.2 프로세스 배포 |
| 4 | Predictable | 프로세스가 측정·분석되어 결과(품질)가 예측됨 | PA 4.1, 4.2 |
| 5 | Innovating | 지속적인 프로세스 개선이 이루어짐 | PA 5.1, 5.2 |

### A-SPICE와 V-Model의 연관성

#### V-Model 단계별 A-SPICE 프로세스 적용

| **V-Model 단계** | **A-SPICE 프로세스** | **설명** |
| --- | --- | --- |
| 요구사항 정의 | SYS.1 요구사항 도출, SYS.2 시스템 요구사항 분석 | 고객 요구사항을 수집하고 시스템 요구사항으로 정리 |
| 시스템 설계 | SYS.3 시스템 아키텍처 설계 | 요구사항에 기반한 시스템 구조 설계와 인터페이스 정의 |
| 소프트웨어 요구사항 분석 | SWE.1 SW 요구사항 분석 | 시스템 요구사항에서 SW 요구사항을 추출하고 상세화 |
| 소프트웨어 설계 | SWE.2 SW 아키텍처 설계 | SW 컴포넌트 구조와 동적 동작 설계 |
| 상세 설계 및 구현 | SWE.3 SW 상세 설계 및 유닛 구현 | 유닛 설계와 코드 작성 |
| 단위 검증 | SWE.4 SW 유닛 검증 | 유닛이 상세 설계를 만족하는지 검증 |
| SW 통합 테스트 | SWE.5 SW 통합 및 통합 테스트 | 유닛을 통합하며 인터페이스와 동작 검증 |
| SW 검증 | SWE.6 SW Qualification Test | SW 전체가 SW 요구사항을 만족하는지 검증 |
| 시스템 통합 테스트 | SYS.4 시스템 통합 및 통합 테스트 | SW와 HW를 통합해 시스템 아키텍처대로 동작하는지 검증 |
| 시스템 검증 | SYS.5 시스템 Qualification Test | 시스템이 시스템 요구사항을 충족하는지 검증 |

(A-SPICE 3.1 기준. 4.0에서는 SWE.4~6, SYS.4~5의 이름이 "Verification" 중심으로 바뀌고 VAL.1이 추가되었다.)

### A-SPICE의 장점

1. **품질 보증** : 체계적인 프로세스를 통해 일관된 품질 보장
2. **리스크 관리** : 프로세스 관리로 프로젝트 진행 중 발생 가능한 리스크 최소화
3. **표준화** : 공통 기준으로 OEM과 공급사 간 소통과 신뢰 확보
4. **효율성 개선** : 반복 가능하고 최적화된 프로세스로 비용 및 시간 절감

---

### A-SPICE와 ISO 26262의 관계

- **A-SPICE**는 소프트웨어 개발 프로세스 품질에 중점을 둔다.
- **ISO 26262**는 기능 안전(Functional Safety)을 다루며, A-SPICE와 같은 구조의 프로세스 위에서 안전성을 보장한다.
- 두 표준은 상호 보완적이며, 함께 사용해 품질과 안전성을 동시에 확보한다. ([SW 안전과 ISO 26262](/2025-01-22-ISO-26262/))

## Automotive SPICE 프로세스 모델의 구성

1. **프로세스 참조 모델 (PRM, Process Reference Model)**
   평가 대상 프로세스의 범위와 프로세스별 정의. 프로세스 **식별자(ID)**, 이름, 목적, 성과(Outcome)로 구성된다.

2. **프로세스 평가 모델 (PAM, Process Assessment Model)**
   프로세스 성과(Outcomes)와 프로세스 속성 성과(Process Attribute Outcomes)가 심사 대상 조직의 프로젝트에 존재하는지 식별하고 만족하는지 **평가하기 위한 지표**를 정의한다.
   - 프로세스 성과 ↔ **프로세스 수행 지표**(Process performance indicators)
     - Level 1에 해당하며 Process outcomes로 평가된다.
     - 1. 기본 프랙티스(BP, Base Practice) 2. 작업 산출물(WP, Work Product)
   - 프로세스 속성 성과 ↔ **프로세스 능력 지표**(Process capability indicators)
     - Level 2부터 5에 해당하며 Process achievement로 평가된다.
     - 1. 일반 프랙티스(GP, Generic Practice) 2. 일반 자원(GR, Generic Resource)

### 평가 등급

각 프로세스 속성은 N/P/L/F 4단계로 평가한다.

| 등급 | 달성률 |
| --- | --- |
| N (Not achieved) | 0 ~ 15% |
| P (Partially achieved) | 15 ~ 50% |
| L (Largely achieved) | 50 ~ 85% |
| F (Fully achieved) | 85 ~ 100% |

어떤 Level을 받으려면 **해당 Level의 PA는 L 이상, 그 아래 Level의 PA는 모두 F**여야 한다.

### VDA Scope

모든 프로세스를 평가하지 않고, 조금 더 중요한 필수 프로세스만 묶은 평가 범위다. (이전에는 HIS Scope라고 불렸다.)

- SYS.2 ~ SYS.5, SWE.1 ~ SWE.6
- MAN.3 (프로젝트 관리), ACQ.4 (공급자 모니터링)
- SUP.1 (품질 보증), SUP.8 (형상 관리), SUP.9 (문제 해결), SUP.10 (변경 요청 관리)

### 왜 CL2가 가장 중요한가

CL2가 가장 중요한 단계이다. 기본적인 Level 1의 요건(프로세스를 수행하고 산출물을 만든다)을 맞춘 뒤, 그것을 **계획하고 관리**하는 단계이기 때문이다.

- PA 2.1 수행 관리 : 목표와 계획을 세우고, 진행을 모니터링하고, 필요하면 조정한다. 책임과 자원이 정의되어 있다.
- PA 2.2 산출물 관리 : 산출물의 요구사항을 정하고, 문서화·검토·형상 관리한다.
- 즉, "결과가 나왔다"에서 "**계획대로, 관리된 상태로** 결과가 나왔다"로 넘어가는 단계다. 많은 OEM이 공급사에 **VDA Scope CL2**를 요구하는 이유다.

## A-SPICE의 핵심 컨셉

1. **플러그인**
   - 시스템 레벨 프로세스(SYS) 아래에 소프트웨어(SWE), 하드웨어(HWE), 기계(MEE) 등 **도메인별 프로세스를 끼워 넣는** 구조다.
   - 시스템 아키텍처에서 나뉜 요소가 각 도메인의 V 모델로 내려가고, 다시 시스템 통합으로 올라온다.
2. **V-모델** ★★★
   - 왼쪽과 오른쪽의 대응되는 구조, V&V
   - validation : Customer based
   - verification : SPEC based
3. **용어** : `엘리먼트`, `컴포넌트`, `유닛`, `아이템`
   - 엘리먼트 : 아키텍처를 구성하는 요소 (시스템/SW 아키텍처 수준)
   - 컴포넌트 : SW 아키텍처를 구성하는 요소
   - 유닛 : 상세 설계에서 더 이상 나누지 않는 최소 단위
   - 아이템 : 시스템 수준에서 다루는 대상
4. **추적성과 일관성** ★★★★
   1. 추적성 : 요구사항 ↔ 설계 ↔ 코드 ↔ 테스트가 양방향으로 연결되어 있다.
   2. 일관성 : 연결된 산출물끼리 내용이 서로 맞는다. 추적성은 일관성을 확인하기 위한 수단이다.
5. **"합의한다"와 "요약하고 의사소통한다"**
   - 산출물을 만드는 것으로 끝나지 않고, 관련 이해관계자와 합의하고 결과를 공유해야 한다. 의사소통이 중요하다.
6. **"평가한다", "검증기준", "준수 보장"**
   1. 평가한다 : 시스템과 소프트웨어 아키텍처, 소프트웨어 상세 설계의 여러 대안을 평가함
   2. 검증 기준 : 요구사항 검증을 위한 정성적/정량적 충족 기준을 의미
   3. 준수 보장 : 테스트 명세는 V 모델 왼쪽 개발 프로세스의 산출물을 충족하도록 개발되어야 함
7. **"전략"과 "계획"의 관계**
   1. 전략이란 계획을 수립하는 방향이다. 통합 전략을 수립하라 → 통합 계획을 수립하라.
   2. 참고 : (장비, 인력, 절차 등) → 프로세스 → 계획 → 전략
   3. 전략은 프로젝트 목표를 달성하기 위해 프로세스를 수행하기 위한 방안이다. 이를 구체화하고 이해관계자들과 합의하여 계획 형태로 저장한다.

## 용어 정리

| 약어 / 용어 | 의미 |
| --- | --- |
| BP | Base Practice (기본 프랙티스) |
| GP | Generic Practice (일반 프랙티스) |
| GR | Generic Resource (일반 자원) |
| PA | Process Attribute (프로세스 속성) |
| PAM / PRM | Process Assessment Model / Process Reference Model |
| 베이스라인 (Baseline) | 공식적으로 검토되고 합의된 명세서나 제품. 이후 개발의 기초로 활용되며, 공식적인 변경 통제 절차로만 변경될 수 있다. (ISO/IEC/IEEE 24765) |
| 블랙박스 시험 | 시험 아이템의 내부 구조에 대한 지식 없이 수행하는 요구사항 기반 시험 |
| 화이트박스 시험 | 시험 아이템의 내부 구조에 대한 지식을 기반으로 수행하는 시험 |
| 코드 검토 (Code review) | 코드가 의도된 사용에 적합한지 결정하고, 명세서·표준과의 불일치를 식별하기 위해 자격 있는 인원이 수행하는 코드 검사 |
