## 요구사항 정의

요구사항은 고객이 실제로 원하는 것이다.
잘 만든다고 잘 팔리는 것이 아니다. 고객이 원하지 않는 기능을 완벽하게 만드는 것은 낭비다.

### 요구사항 관리의 목적

1. **시스템 구현 기반** : 무엇을 만들지 정하는 기준
2. **시스템 품질 기반** : 무엇을 기준으로 검증할지 정하는 근거
3. **시스템 산정 기반** : 일정, 인력, 비용 산정의 근거
4. **비즈니스 가치 기반** : 고객과 시장에 어떤 가치를 주는지

요즈음에는 2, 4에 집중하는 경향이 있다. 기능을 만드는 것보다 **검증 가능한 품질**과 **고객 가치**가 경쟁력이 되기 때문이다.

오픈소스를 활용해서 개발하는 것이 트렌드다.
기존 요구사항/소스와의 **유사율을 분석하여 크면 재활용**한다. 그래서 요구사항을 재사용 가능한 단위로 잘 정리해 두는 것이 중요하다.

## 소프트웨어 개발 실제

현업에서 요구사항이 흘러가는 모습은 대략 다음과 같다.

```text
고객(OEM) 요구사항 문서 (수백~수천 개 항목)
   ↓ 분석, 협의 (모호한 것 질의, 범위 합의)
시스템 요구사항 → SW 요구사항
   ↓ 설계, 구현
테스트 케이스 (요구사항마다 연결)
   ↓
변경 요청 (개발 중에도 계속 들어옴)
```

- 고객 요구사항은 처음부터 완벽하지 않고, 개발 중에도 계속 바뀐다. 그래서 **변경을 관리하는 능력**이 중요하다.
- 요구사항 하나가 바뀌면 어떤 설계, 코드, 테스트가 영향을 받는지 바로 알 수 있어야 한다. 이것이 추적성이다.

### 요구공학 전체 프로세스

**Elicitation - Analysis - Specification - Verification**

| 단계 | 하는 일 | 방법 |
| --- | --- | --- |
| **Elicitation (도출)** | 이해관계자로부터 요구사항을 수집 | 인터뷰, 워크숍, 관찰, 기존 문서 분석, 프로토타이핑 |
| **Analysis (분석)** | 충돌·누락 확인, 기능/비기능 분류, 우선순위 결정, 타당성 검토 | 모델링(유스케이스, 상태도), 리스크 분석 |
| **Specification (명세)** | 합의된 요구사항을 문서화 | 요구사항 명세서(SRS), EARS 같은 정형화된 문장 |
| **Verification (검증)** | 명세가 올바르고 완전한지 확인 | 리뷰, 인스펙션, 체크리스트 |

그리고 이 네 단계 전체에 걸쳐 **요구사항 관리(변경 관리, 추적성 관리, 베이스라인)** 가 이어진다.

자세한 내용과 EARS 작성법은 [V-Model 개발 프로세스와 요구공학](/2025-01-22-V모델-개발프로세스/)에 정리했다.

## 요즘 모델들의 특징

기존에는 Excel로 실제 문서화했던 부분들을 현재는 형상관리 툴(ALM)을 이용해서 **링크**로 관리한다. 요구사항, 설계, 테스트가 서로 연결되어 있어서 하나가 바뀌면 영향받는 항목이 자동으로 표시된다.

강의에서 소개된 요구공학 모델의 방향성은 다음과 같았다.

- **REflex** : 요구사항을 유연하게 (변경에 빠르게 대응)
- **CORE** : 고객 가치 중심
- **Qure** : 품질 중심
