차량용 통신 과정에서 배운 흐름을 정리한다. 큰 순서는 **CAN 기초 → CANoe/CANalyzer 측정·분석 → CANoe 시뮬레이션(CAPL) → 진단**이다.

## CAN Fundamentals

### 1. CAN 통신 개요

- 1980년대 Bosch가 차량 내 배선을 줄이기 위해 만든 **멀티 마스터 직렬 버스**다.
- CAN_H, CAN_L 두 선의 **전압 차(차동 신호)** 로 0/1을 표현해 노이즈에 강하다.
- 버스 양 끝에 **120Ω 종단 저항**을 둔다.
- 메시지에는 목적지 주소가 없고 **ID(식별자)** 만 있다. 모든 노드가 받고, 필요한 ID만 골라 쓴다.

### 2. CAN 프로토콜의 특성

- **우선순위 중재(Arbitration)** : 여러 노드가 동시에 보내면, 비트 단위로 비교해 0(Dominant)이 1(Recessive)을 이긴다. 그래서 **ID가 작을수록 우선순위가 높고**, 진 노드는 데이터를 잃지 않고 나중에 다시 보낸다.
- **프레임 구조 (CAN 2.0A)**

```text
| SOF | ID(11) | RTR | IDE | r0 | DLC(4) | DATA(0~8 byte) | CRC(15) | ACK | EOF |
```

- 표준 ID는 11비트(2.0A), 확장 ID는 29비트(2.0B)다.
- **에러 처리** : 각 노드가 송신/수신 에러 카운터(TEC/REC)를 관리하며, 에러가 쌓이면 Error Active → Error Passive → **Bus Off**로 바뀌어 고장 난 노드가 버스 전체를 망가뜨리지 않게 스스로 빠진다.

### 3. CAN FD

| 구분 | CAN | CAN FD |
| --- | --- | --- |
| 데이터 길이 | 최대 8바이트 | 최대 64바이트 |
| 속도 | 최대 1 Mbps | 중재 구간은 동일, **데이터 구간만 고속**(BRS 비트) |
| 용도 | 일반 제어 | 데이터량 증가, SecOC(MAC 추가) |

### 4. 데이터베이스의 이해 (DBC)

- 네트워크의 **노드, 메시지(ID, DLC, 주기), 신호(시작 비트, 길이, 바이트 순서, Factor/Offset, 단위)** 를 정의한 파일이다.
- 물리값 = Raw 값 × Factor + Offset
- CANoe와 AUTOSAR 설정이 모두 이 정보를 기준으로 하므로, 차량 통신 개발의 **기준 문서**다. 편집은 CANdb++로 한다.

## CANoe / CANalyzer Measurement and Analysis

1. **CANoe, CANalyzer 소개**
   - CANalyzer : 실제 버스를 **측정·분석**하는 도구
   - CANoe : 측정·분석 + **가상 노드 시뮬레이션**과 테스트까지 가능
2. **CANoe, CANalyzer 시작** : 하드웨어(VN 시리즈) 채널 설정, 보오레이트 맞추기, DBC 연결
3. **측정 및 분석**
   - **Trace** : 메시지를 시간순으로 확인 (ID, DLC, 데이터, 주기)
   - **Graphics** : 신호 값을 그래프로 확인
   - **Statistics** : 버스 부하율, 에러 프레임 수
   - 필터와 트리거로 원하는 구간만 기록
4. **데이터 송신** : Interactive Generator(IG)로 메시지를 직접 만들어 보내기
5. **패널** : 버튼, 스위치, 램프로 신호를 조작하고 확인하는 GUI 구성

## CANoe Simulation

1. **시뮬레이션과 모델링 소개** : 실제 ECU가 없어도 가상 노드로 네트워크 전체를 재현(Rest-bus Simulation)해서 개발 초기에 검증한다.
2. **CAPL 프로그램** : C와 비슷한 이벤트 기반 스크립트 언어

   ```c
   variables {
     message EngineData msgEngine;   // DBC에 정의된 메시지
     msTimer t100;
   }

   on start {
     setTimer(t100, 100);
   }

   on timer t100 {
     msgEngine.EngSpeed = 2000;      // 신호 단위로 값 설정
     output(msgEngine);              // 버스로 송신
     setTimer(t100, 100);            // 100ms 주기 반복
   }

   on message GearBoxInfo {
     write("Gear = %d", this.Gear);  // 수신 시 처리
   }
   ```

3. **신호 기반의 CAPL 프로그램 방법** : 메시지 바이트를 직접 다루지 않고 `$Signal` 처럼 **신호 이름으로 읽고 쓰는** 방법. DBC가 바뀌어도 코드를 덜 고친다.
4. **CAPL을 이용한 CAN 데이터 제어** : 패널 입력(`on sysvar`), 키 입력(`on key`)으로 신호를 바꾸고 결과를 확인

## 차량 통신 진단 테스트

- 진단은 정비 장비(Tester)가 ECU에 요청을 보내고 응답을 받는 **Client-Server** 통신이다.
- 응용 계층은 **UDS(ISO 14229)**, CAN에서의 전송은 **CAN TP(ISO 15765)** 가 맡는다. 8바이트를 넘는 데이터는 First Frame / Consecutive Frame으로 나눠 보낸다.

| 서비스 ID | 이름 | 용도 |
| --- | --- | --- |
| 0x10 | Diagnostic Session Control | 기본/확장/프로그래밍 세션 전환 |
| 0x22 / 0x2E | Read / Write Data By Identifier | DID로 데이터 읽기/쓰기 |
| 0x27 | Security Access | Seed & Key 인증 |
| 0x19 / 0x14 | Read / Clear DTC | 고장 코드 조회/삭제 |
| 0x31 | Routine Control | 특정 루틴 실행 |
| 0x34 / 0x36 / 0x37 | Request Download / Transfer Data / Exit | 소프트웨어 리프로그래밍 |
| 0x3E | Tester Present | 세션 유지 |

- 긍정 응답은 `요청 SID + 0x40`(예: 0x22 → 0x62), 부정 응답은 `0x7F + SID + NRC`다.

## cf) CAN과 이더넷의 차이

최소한 1, 2, 7 계층이 완성이 되어야 최소한의 통신이 가능한 디바이스가 만들어진다.

CAN은 송신자가 수신자를 결정하지 않음
이더넷의 Switch는 A를 보낸거를 받아서 A 주소를 확인 한 후 B로 보낸다. 즉 송신자에서 수신자를 결정해서 보낸다고 할 수 있다. 이것이 두 통신간의 가장 큰 차이이다.
그렇기 때문에 CAN에서 수신자를 결정할 수 없는 것이다. 따라서 Gateway에서 수신자로 보내는 CAN Gateway가 있는 것이다. 여기서 User application이 구현되어 있다.

- gateway : 한 개 이상의 프로토콜을 제공하는 장치, 2개 이상의 port. 계층별로 프로토콜이 일치해야 함.

| 구분 | CAN | Ethernet |
| --- | --- | --- |
| 주소 | 메시지 ID (내용 식별) | MAC/IP 주소 (목적지 식별) |
| 수신자 결정 | 수신 노드가 ID로 필터링 | 송신자가 목적지 지정, 스위치가 전달 |
| 토폴로지 | 버스 | 스위치 기반 Point-to-Point |
| 충돌 처리 | 비트 중재 (손실 없음) | 스위치 큐잉 |
