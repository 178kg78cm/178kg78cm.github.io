자동차 소프트웨어 개발 프로세스(A-SPICE, ISO 26262)를 배우면서 "왜 이렇게까지 해야 하나"에 대한 답으로 자주 언급되는 사건이 도요타 급발진 사건이다.

## 사건 개요

- 2009~2010년 미국에서 도요타·렉서스 차량의 의도치 않은 가속(급발진) 사고가 잇따랐다.
- 도요타는 처음에 **바닥 매트 걸림**과 **가속 페달 고착**을 원인으로 보고 대규모 리콜을 진행했다.
- 미국 도로교통안전국(NHTSA)은 NASA에 전자 스로틀 제어 시스템(ETCS) 분석을 의뢰했고, 2011년 보고서는 **전자/소프트웨어 결함의 증거를 찾지 못했다**고 결론 내렸다. 다만 분석 기간과 범위가 제한적이었다는 점도 함께 밝혔다.

## 소프트웨어가 문제로 지목된 재판

2013년 미국 오클라호마의 급발진 사망 사고 재판(Bookout v. Toyota)에서, 소스 코드를 검토한 임베디드 소프트웨어 전문가의 증언이 큰 주목을 받았다. 보도된 주요 지적은 다음과 같다.

| 지적 사항 | 의미 |
| --- | --- |
| **수천 개 이상의 전역 변수** | 어느 함수가 어떤 값을 바꾸는지 추적이 사실상 불가능 |
| **과도한 순환 복잡도** (스파게티 코드) | 테스트와 리뷰로 모든 경로를 검증하기 어려움 |
| **스택 오버플로 가능성** | 스택 사용량 분석이 부족해, 넘치면 다른 데이터를 덮어쓸 수 있음 |
| **단일 태스크 실패 시 제어 상실** | 스로틀 제어 등 여러 기능을 맡은 태스크가 죽으면 이를 감지·복구할 장치가 부족 |
| **MISRA-C 등 코딩 규칙 위반 다수** | 안전 필수 시스템에서 요구되는 코딩 표준을 따르지 않음 |

배심원은 도요타의 책임을 인정했고, 이후 도요타는 관련 소송들을 합의로 정리했다.

## 지금의 개발 프로세스와 연결해 보면

| 사건에서 지적된 문제 | 현재의 대응 |
| --- | --- |
| 코딩 규칙 미준수 | **MISRA-C** 준수와 정적 분석 도구로 자동 검사 |
| 높은 복잡도 | 순환 복잡도 기준(HIS Metrics 등) 관리, 리팩토링 |
| 스택 오버플로 | 정적 스택 분석, AUTOSAR OS의 **Stack Monitoring** |
| 태스크 실패 미감지 | 워치독, AUTOSAR OS의 **Timing/Memory Protection**, Lockstep 코어 |
| 안전 분석 부족 | **ISO 26262** HARA → 안전 목표 → ASIL에 맞는 검증 |
| 추적성 부족 | **A-SPICE**의 양방향 추적성, 형상 관리 |

결국 A-SPICE와 ISO 26262가 요구하는 문서와 절차는 **"우리 소프트웨어가 안전하다는 것을 설명할 수 있는 근거"** 를 만드는 과정이다.
