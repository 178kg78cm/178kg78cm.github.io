## 우선순위 역전이란?

우선순위 기반 선점형 스케줄러에서는 항상 **준비(Ready) 상태인 태스크 중 우선순위가 가장 높은 태스크**가 CPU를 사용한다.
그런데 공유 자원(Resource, Mutex)이 끼어들면 **높은 우선순위 태스크가 낮은 우선순위 태스크 때문에 기다리는** 상황이 생긴다. 이것을 우선순위 역전(Priority Inversion)이라고 한다.

## 발생 시나리오

우선순위가 `H > M > L`인 태스크 3개와 공유 자원 R이 있다고 하자.

```text
시간 →
L : [R 획득]──────┐                      ┌──[R 해제]
H :               └─(R 요청, 대기)·······│···········[R 획득, 실행]
M :                    [M 실행 ─────────]┘
```

1. L이 자원 R을 획득하고 임계 구역을 실행한다.
2. H가 깨어나 L을 선점하지만, R이 이미 L에게 잡혀 있어 **대기(Waiting)** 상태가 된다.
3. 이때 R과 무관한 M이 깨어나면, M은 L보다 우선순위가 높으므로 **L을 선점**한다.
4. L이 실행되지 못하니 R도 해제되지 않고, 결국 **H는 M이 끝날 때까지 기다린다.**

H가 L을 기다리는 것(Bounded)은 임계 구역 길이만큼이라 예측 가능하다. 문제는 3번처럼 **중간 우선순위 태스크가 끼어들어 대기 시간이 무한정 길어지는 것(Unbounded)** 이다. 실시간 시스템에서는 데드라인을 보장할 수 없게 되므로 치명적이다.

> 유명한 사례로 1997년 화성 탐사선 Mars Pathfinder가 우선순위 역전 때문에 워치독 리셋을 반복한 일이 있다. VxWorks의 mutex에 우선순위 상속 옵션을 켜는 것으로 원격 수정했다.

## 해결 방법

### 1. Priority Inheritance Protocol (PIP, 우선순위 상속)

- 높은 우선순위 태스크가 자원을 기다리면, **자원을 가진 태스크가 그 우선순위를 일시적으로 물려받는다.**
- 위 예시에서 H가 R을 기다리는 순간 L의 우선순위가 H로 올라가므로 M이 L을 선점할 수 없다.
- L이 R을 해제하면 원래 우선순위로 돌아온다.
- 단점: 자원이 여러 개면 상속이 연쇄적으로 일어나고(Chained blocking), **데드락은 막지 못한다.**

### 2. Priority Ceiling Protocol (PCP, 우선순위 상한)

- 각 자원에 **그 자원을 사용할 수 있는 태스크 중 가장 높은 우선순위(Ceiling)** 를 미리 정해 둔다.
- 태스크가 자원을 획득하는 즉시 우선순위가 Ceiling으로 올라간다.
- 자원을 쥔 태스크는 그 자원을 쓰는 다른 어떤 태스크에게도 선점되지 않으므로,
  - 블로킹은 **최대 한 번, 임계 구역 하나 길이**로 제한되고
  - 자원을 중첩해서 잡는 순서가 꼬일 수 없어 **데드락도 발생하지 않는다.**

## OSEK / AUTOSAR OS에서는?

OSEK OS는 **Immediate Ceiling Priority Protocol(OSEK PCP)** 를 표준으로 채택했다.

```c
TASK(TaskL)
{
    GetResource(Res_Shared);     // 즉시 Res_Shared의 Ceiling 우선순위로 상승
    /* 임계 구역 : 공유 데이터 접근 */
    ReleaseResource(Res_Shared); // 원래 우선순위로 복귀, 필요하면 재스케줄링
    TerminateTask();
}
```

- 자원의 Ceiling 값은 OIL/ARXML 설정에서 **그 자원을 사용하는 태스크 목록**을 보고 생성 도구가 정적으로 계산한다.
- 그래서 OSEK의 리소스 제약 사항이 생긴다.
  - 같은 자원을 중첩해서 획득할 수 없다.
  - 자원을 쥔 채로 `TerminateTask()` 하거나 `WaitEvent()` 할 수 없다.
  - 여러 자원은 **LIFO 순서**로 획득/해제해야 한다.

## 정리

| 구분 | PIP | PCP (OSEK) |
| --- | --- | --- |
| 우선순위 상승 시점 | 높은 태스크가 **대기할 때** | 자원을 **획득하는 즉시** |
| 필요한 정보 | 없음 (런타임 처리) | 자원별 사용 태스크 (정적 설정) |
| 블로킹 횟수 | 여러 번 가능 | 최대 1번 |
| 데드락 방지 | X | O |
